Getting Started with CIRRUS

Learn how CIRRUS works and how to get your workload running.
Our team can walk you through it, or you can go at your own pace.

How Does CIRRUS Work?

Like NCAR's HPC systems, CIRRUS is a cluster of servers.
Instead of a batch scheduler running jobs that start and finish, it runs Kubernetes.
Kubernetes keeps containers running at scale across all of those servers.

Containers package your code

Like a shipping container, a software container works the same way no matter what's inside or where it goes. A Containerfile (or Dockerfile) lists how to install and run your code, and that builds an image holding only your code and what it needs. The image runs the same on your laptop, a colleague's machine, or CIRRUS, and it can be stored in a container registry, an online library for images, so it's easy to share. You don't have to build everything yourself, either: many tools, such as databases, web servers, and JupyterHub, already publish ready-to-use images you can run as is or build on.

Kubernetes keeps containers running

On its own, a container runs on one machine, and if it stops, it stays down until someone notices. Kubernetes (Greek for helmsman) runs containers across a whole cluster of servers. You tell it what to run, how many copies, and what resources they need, and it keeps it that way. It restarts anything that fails, balances traffic between copies, and moves your workload off a server during maintenance without taking it offline.

Your deployment is defined in code

What Kubernetes should run is written in YAML, plain-text configuration files, often bundled together as a Helm chart. Those files live in a git repository alongside your code, so every change is tracked and your work is reproducible on any Kubernetes cluster.

Continuous delivery keeps it up to date

Continuous delivery means changes are deployed automatically as soon as they land in git, instead of someone logging in to update things by hand. CIRRUS uses a continuous delivery tool called Argo CD. It watches your git repository and automatically syncs what is running on CIRRUS to match it, so updating your workload is just pushing a change to git. If something goes wrong, rolling back is as simple as reverting that change.

The CIRRUS team runs the platform

We maintain the servers and Kubernetes, and provide shared services like certificates, web addresses, storage, and monitoring. You focus on your code.

Working With the CIRRUS Team

You don't need to know containers or Kubernetes to get started. Most projects begin with a conversation.

Reach out. Tell us what you want to run, whether it's an idea or code that's ready to go. We'll set up a meeting to talk through your project and the next steps.

Get your space. We create a namespace for your project: your own area of the cluster for you and your team, a bit like an HPC allocation, with limits on the resources it can use.

Package and deploy together. We help get your code into git, package it into a container, and write the Helm chart or manifests to deploy it. Then we connect your repository to Argo CD so updates roll out automatically.

Learn at your own pace. Go as deep as you want over time. We can also help automate testing and builds as your project grows.

Deploying a Workload on CIRRUS

Here's what it takes to go from code on your laptop to a workload, in this example a Python-based Flask web application, running on CIRRUS at its own URL.

1

Build a Container Image

A Containerfile (or Dockerfile) lists how to install and run your code. Building it produces an image, which you push to any container registry CIRRUS can pull from, public or private, such as GitHub Container Registry, Docker Hub, Quay, or the CIRRUS container registry, Harbor. If a ready-made image already does what you need, such as a database or web server, you can skip building and use it directly.

Example Containerfile for a Python web app:

FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]

Build the image and push it to a registry, for example Harbor:

docker build -t hub.k8s.ucar.edu/your-project/your-app:v1.0 .
docker push hub.k8s.ucar.edu/your-project/your-app:v1.0
Containerization Guide
2

Describe How It Runs

Next, tell Kubernetes how to run that image: how many copies, how much CPU and memory, which port it listens on, and the URL it should be reachable at. This is written in YAML, either as plain manifests or as a Helm chart. Most CIRRUS applications use a Helm chart, where the settings you change most often live in a single values.yaml file.

Example values.yaml:

replicaCount: 2                  # run two copies, with traffic balanced between them

webapp:
  name: your-app
  tls:
    fqdn: your-app.k8s.ucar.edu    # the URL; DNS and the certificate are set up for you
  container:
    image: hub.k8s.ucar.edu/your-project/your-app:v1.0
    port: 5000
    memory: "1G"
    cpu: "1"

ingress:
  className: traefik-external     # traefik-internal keeps it on the UCAR network only

Never put passwords or other sensitive information in values.yaml. For those values, use the CIRRUS secrets manager, OpenBao.

You don't have to start from scratch. The CIRRUS examples repository has charts for common application types.

Helm Chart Guide
3

Put It in Git

Your code, Containerfile, and Helm chart all live together in one git repository. That repository becomes the single source of truth for what runs on CIRRUS.

your-repo/
├── src/                # your application code
├── Containerfile       # how the image is built
├── helm/               # how it runs on CIRRUS
│   ├── Chart.yaml
│   ├── values.yaml
│   └── templates/
└── .github/
    └── workflows/      # automated builds (optional)
4

Connect It to CIRRUS

This is the one step that goes through the CIRRUS team, and it only happens once. Send us your repository URL, the branch to deploy from, and the path to your Helm chart. We connect the repository to Argo CD, and Argo CD deploys your application to your CIRRUS namespace and it's live.

Add Your Workload Open a Jira Ticket
5

Ship Updates Through Git

From here on, updating your application never involves logging in to a server. Build and push a new image, change the image tag in values.yaml, and push that change to git. Argo CD sees it and rolls out the new version. If something goes wrong, revert the commit and the previous version comes back.

You can automate the whole loop with GitHub Actions so that every push builds a new image and updates the chart for you. CIRRUS provides GitHub Actions runners for the NCAR GitHub organization, with more resources than GitHub's free runners and GPU access when you need it.

Accessing the Platform

You don't need cluster access to run on CIRRUS. Access is for seeing what's happening and doing things yourself.

What you can access. Watch your workload in the Argo CD UI, read its logs through Argo CD or kubectl, store images in Harbor, view metrics and logs in Grafana, or manage secrets in OpenBao. Each one is optional and independent, so request only what you need.

How to get it. You sign in with your existing UCAR SSO credentials. Kubernetes and Argo CD access is scoped to your namespace, and is set up through a quick Jira ticket.
