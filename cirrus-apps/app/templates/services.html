CIRRUS Services

Every application starts with the same core platform. These services let you add databases, secrets, workflows, and more when your application needs them.

The Core Platform

Every application on CIRRUS is built from the same three pieces: container images stored in a registry, a Helm chart that describes how it runs, and a Git repository that Argo CD watches and keeps in sync with the cluster.

The services below are different. None of them are required, and most applications only use a few. Each one is available when your application needs it: a PostgreSQL database, secure credential storage, batch workflows, serverless functions, multi-node MPI jobs, and more. Pick a service to see what it does, and how to add it to your application.

Argo CD

Used by every application

Argo CD is the GitOps engine at the heart of CIRRUS. It continuously watches your Git repository and keeps what is running on the cluster in sync with the Helm chart you have committed. There is no deploy button and no kubectl access required: pushing to Git is how you deploy.

How it works for your application

During onboarding the CIRRUS team registers your application with three pieces of information:

  • Git repository URL — where your code and Helm chart live
  • Branch — the branch to deploy from (e.g. main)
  • Chart path — the folder containing your Helm chart

From then on, any change merged to that branch is automatically synced to the cluster. You can log in to the Argo CD UI to watch syncs, view application health, and inspect the live state of your resources.

Access

Your application is deployed and kept in sync without you needing any access. A CIRRUS admin registers your repository and Argo CD takes it from there. You only need access if you want to log in to the UI yourself to watch syncs, check application health, or read your workload's logs. Open a Jira ticket and we will give you access to your application's resources in Argo CD.

Container Registry

Used by every application

Every application on CIRRUS runs from a container image, and the cluster needs a registry to pull that image from. Which registry is up to you: public registries like GitHub Container Registry (GHCR), Docker Hub, and Quay all work out of the box. If your image is already published to one of them, there is nothing more to set up.

Harbor

CIRRUS also runs Harbor, a private container registry hosted on the cluster itself. Projects in Harbor are private to your team by default, but can be made public to share images with the general public. And because Harbor sits local to the cluster, image pulls never leave the data center. Deployments and pod restarts are noticeably faster, especially for large images.

Pushing your images

docker login hub.k8s.ucar.edu
docker build -t hub.k8s.ucar.edu/your-project/your-app:v1.0 .
docker push hub.k8s.ucar.edu/your-project/your-app:v1.0

Beyond the basics

  • Robot accounts let CI/CD pipelines push images without using your personal credentials.
  • Vulnerability scanning runs on pushed images so you can see known CVEs before deploying.

Access

Harbor is entirely optional. Your workload can pull its image from Docker Hub, GHCR, or any public registry without it, so reach for Harbor only if you would rather host images on-cluster. It is open to any UCAR employee by default: sign in with your SSO credentials and you can browse and pull from existing projects right away. To create your own project and manage who can push to it, open a Jira ticket and the CIRRUS team will set it up.

Argo Rollouts

Optional add-on

Argo Rollouts adds progressive delivery to your deployments. Instead of replacing every pod at once when you ship a new version, a rollout can shift traffic gradually: send 25% of users to the new version, pause, check that nothing broke, and continue, with automatic rollback if things go wrong.

When to use it

Most applications are fine with a standard Kubernetes Deployment. Reach for Rollouts when your application has real users who would notice a bad release: public-facing dashboards, APIs that other groups depend on, or services where you want to validate a new version on live traffic before committing to it.

Adding it to your app

In your Helm chart, a Rollout replaces your Deployment and adds a release strategy:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  # ...same pod template as a Deployment...
  strategy:
    canary:
      steps:
        - setWeight: 25
        - pause: {duration: 10m}
        - setWeight: 50
        - pause: {duration: 10m}

Web Access (Ingress)

Optional add-on

By default your application runs inside the cluster and is not reachable from a browser. To give it a URL, add an Ingress to your Helm chart. CIRRUS uses Traefik as its ingress controller, which routes incoming requests to your application and gives it an https://<your-app>.k8s.ucar.edu address.

Internal vs. external access

Which audience can reach your application is set by the ingress class you choose:

  • traefik-internal — reachable only from within the UCAR network or VPN. The right choice for internal tools and dashboards.
  • traefik-external — reachable from the public internet. Use this for applications that need to serve users outside UCAR.

TLS and DNS are automatic

You do not configure certificates or DNS yourself. Once your Ingress exists, ExternalDNS creates the matching DNS record under *.k8s.ucar.edu, and cert-manager issues and renews a Let's Encrypt TLS certificate so your application is served over HTTPS. Defining the Ingress is all it takes.

Adding it to your app

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
spec:
  ingressClassName: traefik-external   # or traefik-internal
  rules:
    - host: my-app.k8s.ucar.edu
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-app
                port:
                  number: 80

CloudNativePG

Optional add-on

CloudNativePG (CNPG) is a Kubernetes operator that runs production-grade PostgreSQL clusters inside CIRRUS. Instead of managing your own database server, you describe the cluster you want in YAML and the operator handles replication, failover, and backups.

When to use it

Any application that needs a relational database: storing user submissions, caching processed results, backing a web framework like Django or Flask with SQLAlchemy. Because the database runs next to your application in the cluster, there are no external connection or firewall hoops.

Adding a database to your app

Add a Cluster resource to your Helm chart templates:

apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: my-app-db
spec:
  instances: 2
  storage:
    size: 5Gi

CNPG automatically creates a Kubernetes Secret named my-app-db-app containing the connection credentials. Reference it from your application's environment instead of hard-coding anything:

env:
  - name: DATABASE_URI
    valueFrom:
      secretKeyRef:
        name: my-app-db-app
        key: uri

Persistent Storage

Optional add-on

Containers start with an empty disk and lose whatever they wrote when they stop. To keep files around, ask the cluster for a volume: anything written to one survives pod restarts, redeployments, and node failures. CIRRUS backs these volumes with Ceph, a distributed storage system, and offers them in two flavors — a disk for a single pod, or a shared filesystem many pods can mount at once. For data you would rather reach by key than mount as a directory, see Object Storage, which is also Ceph-backed.

Requesting a volume

Add a PersistentVolumeClaim to your Helm chart and pick the storage class that matches how the volume will be used:

  • ceph-kubepv (Ceph RBD) — block storage with ReadWriteOnce access. One pod mounts it read-write at a time, making it the right choice for databases, caches, and any single-pod application state. CloudNativePG database clusters use this class for their storage.
  • cephfs (CephFS) — a shared filesystem with ReadWriteMany access. Multiple pods can read and write the same volume simultaneously, which fits shared scratch space, datasets read by several replicas, or pipelines where one job writes files that another consumes.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-app-data
spec:
  storageClassName: ceph-kubepv   # or cephfs for shared access
  accessModes:
    - ReadWriteOnce               # ReadWriteMany with cephfs
  resources:
    requests:
      storage: 10Gi

Mount the claim as a volume in your pod spec and your application sees an ordinary directory.

Sizing and backups

A claim's size is what you reserve, so ask for what your data needs plus headroom rather than the largest number you can imagine. Volumes are replicated by Ceph, which protects you from hardware failure — it does not protect you from your own application deleting or corrupting its data. If a volume holds something you cannot regenerate, plan a backup: CloudNativePG can back a database up on a schedule, and other workloads commonly copy snapshots to object storage.

Access

No request needed. Volumes are provisioned automatically from the claim in your Helm chart the first time your application deploys. If you need an unusually large volume, mention it in your onboarding ticket so we can check capacity.

Object Storage (S3)

Optional add-on

CIRRUS runs S3-compatible object storage through the Ceph Rados Gateway at https://s3.k8s.ucar.edu:5443, replicated between the ML and NWSC sites for high availability. Instead of mounting a filesystem, you put and get objects by key over HTTP — which means the same bucket is reachable from your workload in the cluster, from a batch job, from a notebook, and from your laptop.

When to use it

Reach for object storage when your data is a collection of whole files rather than something an application needs to read and write in place: model artifacts and checkpoints, processed datasets, backups, or files your application serves and fetches by key. Choose a persistent volume instead when a process needs an ordinary directory — a database's data files, for instance, or anything that appends to a file in place.

Using it

Any S3 tool or library works by pointing it at the CIRRUS endpoint:

# aws cli
aws --endpoint-url https://s3.k8s.ucar.edu:5443 s3 ls s3://your-bucket/

# s5cmd (recommended, much faster)
s5cmd --endpoint-url https://s3.k8s.ucar.edu:5443 ls s3://your-bucket/

Python applications can use boto3 with the same endpoint.

Credentials

There are two ways to authenticate against the gateway:

  • Issued S3 keys — a dedicated access key and secret key that the CIRRUS team creates for you. This is the right choice for an application: the credentials belong to the workload rather than to a person, and they can be stored in OpenBao and injected as a Kubernetes Secret.
  • Your UCAR LDAP credentials — the gateway also accepts an LDAP token in place of an access key, which is handy for interactive use and quick testing without waiting on a key to be issued. Encode your username and password into the token that Rados Gateway expects and use the result as the access key ID:
echo -n '{"RGW_TOKEN":{"version":1,"type":"ldap","id":"<username>","key":"<password>"}}' \
  | base64 -w0

export AWS_ACCESS_KEY_ID="<the base64 string>"
export AWS_SECRET_ACCESS_KEY="unused"   # not checked for LDAP tokens

aws --endpoint-url https://s3.k8s.ucar.edu:5443 s3 ls

The token carries your password in a reversible encoding, so treat it exactly like the password itself: keep it out of shell history, scripts, and Git. For anything long-lived, use issued S3 keys instead.

Access

For issued keys, open a Jira ticket or email the team and we will provide your keys and a bucket. If you would rather authenticate with your UCAR LDAP credentials, no request is needed — see Credentials above.

OpenBao Secret Manager

Optional add-on

OpenBao stores sensitive values such as API keys, passwords, and tokens, encrypted and outside of your Git repository. The External Secrets Operator then injects those values into your application as native Kubernetes Secrets, so nothing sensitive ever appears in your code or Helm chart.

When to use it

Whenever your application needs a credential: a token for an external API, a password for a service you connect to, or any value you would not want visible in a public repository.

Adding secrets to your app

First, log in to OpenBao with your UCAR credentials and store your secret under your user path. Then reference it from your Helm chart with an ExternalSecret:

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: myapp-secrets
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: openbao-backend
    kind: SecretStore
  target:
    name: myapp-secrets
  data:
    - secretKey: my-secret-value
      remoteRef:
        key: your-email@ucar.edu/your-secrets
        property: my-secret-key

The resulting Kubernetes Secret can be mounted or exposed as environment variables like any other.

Access

You only need OpenBao if your workload needs to store or inject secrets. Using it requires a Jira ticket, even for personal access. Once your request is set up, you get a secret engine keyed to your email address, for example ncote@ucar.edu/, that you reach by signing in with your UCAR SSO credentials. If your team needs to share secrets, we can set up a shared secret engine for the group as well; just mention it in your ticket.

Argo Workflows

Optional add-on

Argo Workflows runs multi-step jobs on Kubernetes, where each step is a container. Steps can run in sequence or in parallel, pass artifacts between each other, and run on a schedule. That makes it a natural fit for data processing pipelines that complement an always-on application.

When to use it

What a workflow looks like

Fission

Optional add-on

Fission is the functions-as-a-service (FaaS) provider on CIRRUS. You write a single function — Python, Go, Node.js, Ruby, PHP, Bash, Java, or a plain binary — and Fission runs it on demand when an HTTP request arrives, keeping a small pool of warm pods ready so calls do not wait on a cold start. There is no Dockerfile or Helm chart to write for the simple case.

When to use it

Fission is the lightest-weight way to put code on CIRRUS. It fits small, single-purpose endpoints: a webhook receiver, a lightweight data lookup API, or a glue function that connects two systems. If your code is one function rather than an application, Fission saves you the full containerize-and-chart workflow.

The four pieces

  • Environment — the language runtime your functions plug into. You need one per language, and every function in that language shares it. Environments hold warm pods against your namespace quota, so create them only for languages you actually use.
  • Package — the deployment archive (a zip of your source) plus its build status. Created for you when you deploy from --src.
  • Function — binds a package to an entrypoint, such as myfunc.main.
  • Route (HTTPTrigger) — exposes the function on the shared FaaS gateway at fn.k8s.ucar.edu.

Deploying a function

Create the environment once per language, then the function, then a route:

# once per language, per namespace
fission env create --name python --poolsize=1 \
  --image ghcr.io/fission/python-env \
  --builder ghcr.io/fission/python-builder \
  -n <your-namespace>

# a single-file function
fission fn create --name hello --env python --code hello.py -n <your-namespace>

# expose it at https://fn.k8s.ucar.edu/<username>/hello
fission route create --function hello --name hello --url /<username>/hello \
  --route-provider gateway --gateway traefik/traefik-gateway \
  --route-host=fn.k8s.ucar.edu -n <your-namespace>

URL paths are shared

Every route lives on the same fn.k8s.ucar.edu host, and paths are first-come, first-served across all users and namespaces. Prefix your paths with something you own — your username, team, or project — for example /<username>/hello. If the path is already claimed, the existing route keeps working and yours shows READY False in fission route list. That is the usual meaning of a route stuck at False with no other errors: delete it and pick a different path.

Functions with dependencies

For a few simple pip packages, ship a requirements.txt alongside your module and let Fission's builder do the work. Build status lives on the package, not the function, so watch fission pkg list until BUILD_STATUS reaches succeeded:

zip -r src.zip myfunc.py requirements.txt
fission fn create --name myfunc --env python --src src.zip \
  --entrypoint myfunc.main -n <your-namespace>
fission pkg list -n <your-namespace>

For anything heavier — scientific stacks, conda, a shared internal library — build your own runtime image instead. Extend the Fission runtime (FROM ghcr.io/fission/python-env), bake the dependencies in, push it to Harbor, and point the environment at that image with no builder configured. Your deployment zip then stays tiny and each deploy is reproducible.

Managing functions with GitOps

The fission CLI is the fastest way to get a first function working, but every Fission object can also be written as YAML and reconciled by Argo CD, which is the recommended path for anything you intend to keep running. Each command has a one-to-one manifest equivalent: Environment, Package, Function, and HTTPTrigger. Commit those manifests, add a GitHub Actions workflow that builds your image and archive and pins the image tag, archive URL, and checksum into the manifests, then open a ticket to have the repository onboarded as an Argo CD source. From then on a push deploys your function.

Two details matter when you go this route:

  • Bump an annotation on every release. Warm pool pods cache their specialization, so if new code ships but the Function spec is byte-for-byte identical, warm pods keep serving the old code. Writing the archive checksum into an annotation such as cirrus.ucar.edu/code-checksum forces the spec to change and invalidates that cache.
  • Point packages at an immutable archive. Use a GitHub release asset URL, not a /archive/ auto-generated zip — those are not byte-stable and will break the checksum.

Once a repository is onboarded, Git becomes the only way to change these objects: fission and kubectl commands that modify them hold only until the next sync. Read-only commands are unaffected.

Access

Functions are created and managed entirely through the Kubernetes API, so there is no GUI. Open a Jira ticket or email the CIRRUS team to request FaaS access; you will be given a namespace and, if you do not have it already, access to the Kubernetes API server. You will also need the Fission CLI and kubectl installed locally.

MPI Operator

Optional add-on

CIRRUS runs the Kubeflow MPI Operator, which lets you run MPI (Message Passing Interface) jobs on the cluster the way you would on an HPC system. You submit a single MPIJob resource and the operator creates the launcher and worker pods, distributes SSH keys between them, and manages the job through to completion — no manual pod, service, or MPI runtime wiring.

When to use it

  • Multi-node scientific codes that already use MPI
  • Multi-GPU distributed training with Horovod, PyTorch DDP, or torchrun
  • Benchmarks and test suites that need several nodes' worth of CPU or GPU at once

How an MPIJob is put together

  • Launcher — one pod that runs mpirun and produces the job's output
  • Worker — the pods that do the computation; they run sshd and wait for the launcher
  • slotsPerWorker — MPI ranks per worker pod, usually matched to the CPU or GPU count you request
  • cleanPodPolicy — set it to Running to keep pods around after the job finishes so you can inspect them
apiVersion: kubeflow.org/v2beta1
kind: MPIJob
metadata:
  name: pi
spec:
  slotsPerWorker: 1
  mpiReplicaSpecs:
    Launcher:
      replicas: 1
      template:
        spec:
          containers:
            - name: mpi-launcher
              image: docker.io/mpioperator/mpi-pi:openmpi
              command: ["mpirun"]
              args: ["-n", "2", "/home/mpiuser/pi"]
    Worker:
      replicas: 2
      template:
        spec:
          containers:
            - name: mpi-worker
              image: docker.io/mpioperator/mpi-pi:openmpi
              command: ["/usr/sbin/sshd", "-De", "-f", "/home/mpiuser/.sshd_config"]

Launcher and worker use the same MPI-enabled image. Both need MPI installed, and workers must start an SSH daemon in the foreground — that is how the launcher reaches them.

SSH between launcher and workers

The operator generates SSH keys and mounts them at sshAuthMountPath (usually /root/.ssh). Most images also need ssh_config and sshd_config supplied as ConfigMaps and mounted into the launcher and workers, with StrictHostKeyChecking no on the launcher side and StrictModes no on the worker side. SSH is the most common source of failures: a connection timeout means the worker's sshd is not running, and Permission denied (publickey) means the keys are not mounted where the image expects them.

Running and monitoring a job

kubectl apply -f myjob.yaml
kubectl get mpijob my-mpi-job -w

# mpirun output lands in the launcher
kubectl logs -l training.kubeflow.org/job-name=my-mpi-job -c mpi-launcher

kubectl delete mpijob my-mpi-job

Multi-GPU and multi-node

  • Request GPUs per worker with resources.limits."nvidia.com/gpu" and set slotsPerWorker to match, so you get one rank per GPU.
  • For PyTorch, run torchrun under mpirun and pass the replica count through an environment variable so it matches your worker replicas.
  • Mount a cephfs volume (ReadWriteMany) for datasets and checkpoints that every rank needs to read or write.
  • Jobs stuck in Pending almost always mean the requested CPU, memory, or GPU is not available — check kubectl describe pod before changing anything else.

Submitting jobs from CI

MPIJobs are just Kubernetes resources, so a GitHub Actions workflow running on a CIRRUS runner can submit one, poll status.conditions for Succeeded or Failed, pull the launcher logs, and delete the job. That gives you multi-node regression tests on real cluster hardware. The runner's service account needs permission to create and watch mpijobs plus read pods and pod logs; the same pattern works from any pod in your namespace with that RBAC.

Access

Running MPI jobs needs a namespace and kubectl access to it, since jobs are submitted through the Kubernetes API. Open a Jira ticket to request access, and mention the scale you are aiming for — how many nodes and GPUs — so we can make sure the quota fits.

Grafana, Prometheus & Loki

Optional add-on

CIRRUS runs a full observability stack: Prometheus collects metrics from your application, Loki collects its logs, and Grafana brings both together in dashboards you can build and share. Your application's logs are collected automatically, with no agent or configuration required on your side.

When to use it

  • Troubleshoot a misbehaving application by searching its logs in one place
  • Build a dashboard showing your application's traffic, errors, and resource usage
  • Set up alerts so you hear about problems before your users do

Scraping your application's metrics

Container-level metrics — CPU, memory, network — are collected for every workload with no setup on your part. To see what is happening inside your application, expose your own metrics in Prometheus format, conventionally on /metrics: prometheus_client for Python, prom-client for Node.js, Micrometer for Java, client_golang for Go. Many official images already ship an exporter that just needs enabling in their configuration.

Then give your Service a named metrics port and add a ServiceMonitor so Prometheus knows where to scrape. The release: kube-prometheus-stack label is what lets the monitoring stack discover the monitor — without it, nothing is scraped:

apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
  ports:
    - name: http
      port: 80
      targetPort: 8080
    - name: metrics          # the named port the monitor refers to
      port: 9090
      targetPort: 9090
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: my-app-metrics
  labels:
    release: kube-prometheus-stack   # required for discovery
spec:
  selector:
    matchLabels:
      app: my-app
  endpoints:
    - port: metrics
      path: /metrics
      interval: 30s

A PodMonitor works the same way if you would rather scrape pods directly and skip the Service. Once your metrics are being collected they are queryable in Grafana and can drive custom alerts.

Access

Open a Jira ticket to get access to Grafana for your applications. Your logs and metrics are collected automatically whether or not you ever log in, so you only need access if you want to view them or build dashboards. Grafana uses role-based access control, so permissions are scoped to your team's dashboards and data. Once access is set up, you sign in with your UCAR SSO credentials.

Custom Alerting

Optional add-on

Dashboards tell you what is happening when you go looking. Alerting tells you without being asked. Prometheus evaluates conditions you write against the metrics it collects, and Alertmanager delivers the notification — to email, Slack, PagerDuty, Microsoft Teams, or any webhook. Both the conditions and the routing live in your own Helm chart, so alerting is reviewed and versioned in Git like the rest of your application.

Before you start

You need metrics to alert on and a chart to put the alerts in:

  • Container-level metrics are always available, so alerts on pods being down or memory usage need nothing extra. Alerting on your application's own numbers first requires a monitor that scrapes them.
  • A Helm chart synced by Argo CD, since that is what deploys the two manifests below.

Two manifests

Add both to your existing chart's templates/ directory — they are ordinary resources, not a separate chart:

  • PrometheusRule — the conditions. What to watch and when it counts as a problem.
  • AlertmanagerConfig — the routing. Which alerts it handles, who gets notified, and how often.

Both need the release: kube-prometheus-stack label to be discovered. It is the most common reason a correct-looking alert never does anything.

Defining the conditions

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: my-app-alerts
  labels:
    release: kube-prometheus-stack   # required for discovery
spec:
  groups:
    - name: my-app.rules
      interval: 30s
      rules:
        - alert: PodDown
          expr: up{namespace="my-namespace"} == 0
          for: 5m
          labels:
            severity: critical
            namespace: my-namespace   # what the route below matches on
          annotations:
            summary: "Pod is down in my-namespace"
            description: "A pod has been down for more than 5 minutes."
  • expr — a PromQL expression; the alert is pending whenever it returns anything
  • for — how long the condition must hold before it actually fires, which is what keeps a brief blip from paging you
  • labels — used for routing and grouping. The namespace label is what your Alertmanager route selects on, so keep it on every rule.
  • annotations — the human-readable text that ends up in the notification

Routing the notification

apiVersion: monitoring.coreos.com/v1alpha1
kind: AlertmanagerConfig
metadata:
  name: my-app-alerting
  labels:
    alertmanagerConfig: my-app
    namespace: my-namespace
    release: kube-prometheus-stack
spec:
  route:
    receiver: my-app-notifications
    groupBy:
      - alertname
    groupWait: 10s        # wait this long to batch a new alert group
    groupInterval: 1m     # then this long between updates to that group
    repeatInterval: 60m   # and this long before re-notifying a firing alert
    matchers:
      - name: namespace
        value: my-namespace
        matchType: "="
  receivers:
    - name: my-app-notifications
      emailConfigs:
        - to: team@ucar.edu
          from: alertmanager@k8s.ucar.edu
          smarthost: vdir.ucar.edu:25

The matchers decide which alerts this config is responsible for — matching on your own namespace is the usual choice and keeps you from picking up other applications' alerts. To notify somewhere other than email, swap emailConfigs for the receiver you want (slackConfigs, pagerdutyConfigs, webhookConfigs, opsgenieConfigs, msteamsConfigs); the route above stays as it is. A Slack receiver needs a webhook URL, which belongs in OpenBao rather than in your values.yaml.

Deploying

Commit and push. Argo CD syncs the manifests like any other change, and Prometheus picks up the new rule within a minute or two. Check Argo CD for sync errors if nothing seems to happen.

Test with an always-firing alert first

Alertmanager is not exposed to users on CIRRUS: there is no UI to open and no logs you can read, so a silent notification pipeline gives you nothing to debug. Prove the pipeline works before you rely on it. Add a throwaway rule whose expression is always true, confirm the notification arrives and reads the way you want, then delete the rule and redeploy.

- alert: TestAlert
  expr: vector(1)
  for: 1m
  labels:
    severity: warning
    namespace: my-namespace
  annotations:
    summary: "Test alert - always firing"
    description: "Verifying notification delivery. Remove once confirmed."

When something is wrong

  • Nothing arrives at all — check that the alert's namespace label matches what the route's matchers select, that both manifests carry the release label, and that repeatInterval is not simply suppressing a repeat of an alert you already received. For email, the SMTP smarthost has to be reachable from the cluster.
  • The alert never fires — run the PromQL by hand in Grafana against the Prometheus data source. If it returns nothing there, it will never fire. Also confirm the for duration has actually elapsed.
  • Your own metrics are missing — the monitor's selector.matchLabels has to match the labels on your Service or pods, and the named metrics port has to exist on the Service.

Access

Nothing to request. The manifests live in your chart and Argo CD applies them, so if you can deploy, you can alert. Grafana access is worth having to check your PromQL before you commit it. If your test alert never arrives and the checks above come up clean, open a Jira ticket — we can see the Alertmanager side and you cannot.
