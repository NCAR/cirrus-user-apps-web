CIRRUS Architecture

CIRRUS is two Kubernetes clusters, one at the NCAR Mesa Lab and one at the NCAR-Wyoming Supercomputing Center (NWSC), run by the CIRRUS team.

What Is CIRRUS?

The cloud is just servers someone runs for you, with specialized software on top.
CIRRUS is a cluster of servers the CIRRUS team manages.
It uses Kubernetes and additional software to deliver workloads customized to your research.

CIRRUS is built around Cloud Native principles: workloads are packaged in containers, described in code, and deployed from git. That means anything built to run on CIRRUS can also run on any other Kubernetes cluster, whether on-premises, at another institution, or in a public cloud like AWS, Google Cloud, or Azure. Your work is portable and reproducible, not locked into one environment.

How CIRRUS relates to HPC

CIRRUS is not a replacement for NCAR's HPC systems, it is a complement to them. HPC clusters and their batch schedulers are built for large, finite compute jobs such as model runs and simulations that start, run, and finish. CIRRUS is built for long-running, always-on workloads such as websites, dashboards, APIs, and interactive services that need to stay available around the clock.

Many research groups use both. You might run a simulation on HPC and then use CIRRUS to host a dashboard or API that serves the results to collaborators or the public. Because CIRRUS can mount NCAR storage, the work you do on HPC and the workloads you run on CIRRUS can share the same datasets.

Containers

Everything on CIRRUS runs in a container, a standard package holding only your code and what it needs to run.

A standard way to ship software

The name comes from shipping. A shipping container has a standard size, shape, and set of connections, so it is handled the same way whether it holds pens or Porsches. Software containers work on the same principle: every container is started, stopped, and connected the same way, no matter what is inside. Because a container brings its own dependencies, updates to the server underneath don't conflict with your code, and it runs the same on your laptop, a colleague's machine, CIRRUS, or a public cloud.

Containerfiles and images

A Containerfile (also called a Dockerfile) is a short text file with instructions for installing and running your code, usually starting from a base image such as a specific version of Python. Building it produces an image, a fixed snapshot of your code and its requirements. Images are versioned with tags, like v1.0, so you always know exactly which version is running. Because the Containerfile records how the image was built, anyone can rebuild it the same way.

Container registries

Images can be stored in a container registry, an online library for images that makes them easy to share. CIRRUS can run images from any registry it can reach, public or private, including GitHub Container Registry, Docker Hub, and Quay. CIRRUS also runs its own registry, Harbor, at hub.k8s.ucar.edu, which stores private and public images for your projects and caches images pulled from public registries.

Start from existing images

You don't have to build everything yourself. Many tools, such as databases, web servers, and JupyterHub, publish ready-to-use images you can run as is or use as a base for your own.

Kubernetes

A container on its own runs on one machine, and if it stops, it stays down until someone notices. Kubernetes runs containers across a whole cluster of servers and keeps them running.

Container orchestration

Kubernetes (Greek for helmsman or pilot) is a container orchestration platform, originally developed at Google and donated to the Cloud Native Computing Foundation in 2015. It decides which server each container runs on, restarts containers that fail, and balances traffic between copies. You describe what you want running, and Kubernetes continuously works to keep the cluster matching that description.

Built to stay up

Because your workload can run as multiple copies on different servers, a single server failing doesn't take it offline. Kubernetes moves traffic away from the failed server and starts replacement copies elsewhere. The same mechanism lets the CIRRUS team take servers offline for maintenance and upgrades without interrupting your workload, and lets you roll out a new version gradually instead of all at once.

Defined in YAML and Helm charts

What Kubernetes should run is written in YAML, a plain-text format for configuration files. Each file describes a resource: a Deployment that runs your containers, a Service that gives them a stable network address, an Ingress that routes a URL to them, and so on. Those files can be applied individually, or bundled together as a Helm chart, a reusable package where the settings you change most often live in a single values.yaml file. Because the definitions are plain text, they can be kept in git right next to your code.

Namespaces

A Kubernetes cluster is divided into namespaces. On CIRRUS, each project gets its own namespace: an area of the cluster for you and your team, with limits on the resources it can use, a bit like an HPC allocation. Access to the cluster is scoped to your namespace.

The CIRRUS Platform

Each workload runs on one of the two CIRRUS clusters, using the compute, storage, networking, and security the platform provides.

The two clusters don't provide failover for each other, so if a cluster has an outage, workloads on it aren't automatically served from the other. Workloads can be set up to move between clusters when needed.

Compute and GPUs

Each running copy of your workload lives on a single server and uses only that server's CPU, memory, and GPU. Running multiple copies lets your workload use more of the cluster, with copies usually placed on different servers and traffic automatically load balanced between them by Kubernetes. Some CIRRUS servers include GPUs for workloads like model inference, visualization, and testing code against GPUs.

Storage

Containers start fresh each time they are created, so anything that needs to persist is kept in separate storage. CIRRUS offers several persistent storage options, depending on how your workload needs to store its data. Workloads can also mount NCAR HPC storage directly, giving your workloads access to existing datasets without copying data into the cluster.

Networking and access

Workloads can be made available to the public internet or kept on the UCAR network, depending on what your project needs. Each application gets its own web address secured with HTTPS, with no networking setup required on your part.

Security

Security is enforced at both the cluster and network level. Cluster policies define what workloads are and aren't allowed to do, and network policies control what traffic can reach them. Sensitive values like passwords and API keys are kept in a secrets manager, never in git. You sign in with your UCAR credentials, and role-based access control (RBAC) limits you to only the resources and actions you need.

Observability

Metrics and logs are collected from every workload, and you can view dashboards for your own workloads to see how they are performing and troubleshoot problems.

GitOps and Argo CD

Between your container image and your Kubernetes YAML or Helm chart, everything needed to run your workload is defined in code. GitOps keeps that code in git and uses it to deploy your workload automatically.

Git

Git is a version control system that tracks every change to a set of files over time. Each meaningful change is saved as a commit, a snapshot of your files with a message describing what changed and who changed it. Repositories are pushed to a service like GitHub, where collaborators can work on separate branches and propose changes through pull requests that others review before they are merged. If a change breaks something, the history shows exactly what changed and lets you roll back to a version you know works.

GitOps and continuous delivery

GitOps makes a git repository the single source of truth for what is running. Instead of someone logging in to update things by hand, changes are deployed automatically as soon as they land in git, a practice called continuous delivery. Every deployment is tracked, reviewable, and reversible, and other researchers can use your repository to deploy the same workload themselves.

Argo CD

CIRRUS uses Argo CD, an open source continuous delivery tool, to put GitOps into practice. Argo CD watches the branch and path of your repository that define your application and continuously compares them to what is running on the cluster. When they differ, it syncs the cluster to match git. Rolling back is as simple as reverting a commit. Because each application points at a branch, you can run a development version from one branch alongside production from another, and promote changes by merging a pull request.

Automating builds with GitHub Actions

GitHub Actions can automate the rest of the loop. When you push code, a workflow builds a new container image, pushes it to a registry, and updates the image tag in your Helm chart, which Argo CD then deploys. CIRRUS provides GitHub Actions runners that run these workflows on CIRRUS hardware, with more resources than GitHub's free runners, optional GPU access, and access to NCAR datasets for testing.

Ingress, DNS, and certificates

When someone visits your application, the request reaches the cluster through an ingress controller, which routes it to your containers based on the web address. CIRRUS uses Traefik as its ingress controller, with two ingress classes: traefik-external for applications reachable from the public internet, and traefik-internal for applications reachable only within the UCAR network. External endpoints get publicly accessible IP addresses from LoxiLB, which advertises them over BGP. ExternalDNS automatically creates DNS records in the *.k8s.ucar.edu domain for the name you choose, and cert-manager requests and renews InCommon TLS certificates from CertiNext over ACME to provide HTTPS for your applications.

Persistent storage

CIRRUS uses Ceph for persistent storage, which provides three types: block storage (RBD) for volumes used by a single workload, such as a database; a shared file system (CephFS) that multiple copies of a workload can read and write at once; and object storage for files accessed over an API, similar to Amazon S3. Block and file storage are attached to containers through Kubernetes persistent volumes, so data survives container restarts and can be backed up.

Authentication and access control

You sign in to CIRRUS tools with your existing UCAR SSO credentials. Access is managed with role-based access control (RBAC), which sets both what you can see and what you can do, such as viewing your application in Argo CD read-only or being able to sync it yourself. Depending on your project, access can include Kubernetes API and kubectl for your namespace, Argo CD for your applications, Harbor for your team's images, OpenBao for your secrets, and Grafana for your team's metrics and logs. The Services page covers what access each one offers and how to request it.

Secrets management

OpenBao works with the External Secrets Operator to store sensitive data like API keys, passwords, and credentials. Secrets are encrypted at rest in OpenBao and delivered to your containers encrypted in transit, so sensitive information never lives in your git repository or Helm chart.

Monitoring and logging

Prometheus collects metrics and Loki collects logs from across the cluster. Grafana brings both together, with dashboards and alerts built on top of them. Each team gets its own Grafana organization, so you see your own metrics, logs, and dashboards without seeing anyone else's.

Beyond the Core Platform

The components above are what it takes to run CIRRUS. On top of them, CIRRUS offers many additional services you can build on, such as managed databases, JupyterHub, GitHub Actions runners, and more, each with details on how to use it and request access.
